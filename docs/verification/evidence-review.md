# Phase 3 pure helper review

Reviewed 2026-10-18: `lib/evidence-validation.ts`, `lib/evidence-migration.ts`, `lib/evidence-requirements.ts`, `lib/acceptance.ts`, `lib/decisions.ts`, and plan 03. This is a bounded review of pure groundwork, not acceptance of storage, routes, attachment infrastructure or UI.

## Helper findings and disposition

1. **Resolved: incompatible ID contracts (medium).** `evidence-requirements.ts` accepts subject/criterion IDs up to 200 characters and transforms surrounding whitespace with `.trim()`; `acceptance.ts` does the same for acceptance/evidence/decision/requirement IDs. `evidence-validation.ts:evidenceIdSchema` and `decisions.ts:id` instead cap IDs at 128 and reject surrounding whitespace. A 129-character requirement ID passes the requirement schema but cannot appear in a valid evidence link or decision exception. A padded subject ID is silently changed by one schema and rejected by another. Reuse the canonical evidence ID schema for all identity fields; reject rather than rewrite identities. Add 128/129 and padded-ID interoperability tests across requirement → link → exception → acceptance.

2. **Resolved: candidate values accepted by evidence could not always be accepted by the acceptance schema (medium).** `evidence-validation.ts:evidenceInputSchema` allows candidate strings through 500 characters without changing their content. Requirement and acceptance schemas cap them at 200 and trim them. A legitimate 201-character evidence candidate cannot be represented as an acceptance candidate, and whitespace-preserving evidence can disagree with the transformed acceptance candidate during exact comparison. Pick one shared bounded, non-transforming candidate schema and test exact round-trip behavior. This is an interoperability defect rather than a scope bypass.

The authorized follow-up fix now imports canonical 128-character, non-transforming ID and real-calendar timestamp schemas in both modules; candidate bounds are 500 with exact text preserved, and requirement labels preserve nonblank original text. Added boundary/calendar/round-trip regressions. Descriptions above record the reviewed defect before that fix.

3. **Resolved: contradiction findings lost the exact source identity (low/medium).** `evaluateRequirements` correctly scans all exact-subject/criterion contradictory links even when the caller omits them from selected refs, but reduces them to one boolean and a generic finding. `RequirementFinding` carries no evidence ID/version or link ID. An acceptance preview can therefore say a contradiction exists without identifying the immutable source the owner must inspect; the owner cannot build an exact review list from the returned findings alone. Return bounded exact contradiction refs/link IDs (or a separate resolved contradiction list), retaining every source. Missing/unresolvable contradiction sources should remain explicit findings rather than disappear.

## Required integration gates, not demonstrated helper bugs

- **Imported history is not current authority.** `AcceptancePreviewContext.trustedOrigin` protects the new acceptance action only. Its trusted decision arrays and heads have no provenance discriminator. An imported, schema-valid `decided` record with a matching head would satisfy exception validation if the integration indiscriminately places imported historical claims in those trusted arrays. Likewise pure decision helpers assume authenticated-owner context rather than receiving an authority envelope. The eventual storage/restore/route layer must distinguish historical claims from current owner-authorized decision grants; imported actor/status labels alone must never become trusted exception authority. Verify an imported decided exception cannot waive a new required criterion until an explicit current owner action. No production evidence store/module/routes were present at this review, so this is a release gate rather than a claimed exploitable route.

- **Commit predicates must preserve the preview snapshot.** Pure preview cannot atomically protect evidence heads, links (including unselected contradictions), criteria, decision heads/revocation, attachments or acceptance supersession from changes after assessment. The eventual compiler must reread/guard these in the same shared-revision transaction, record its own time/origin/IDs, and reject client-supplied authority. Test archive/revise/revoke/contradiction insertion/attachment deletion between preview and commit. Attachment signature/byte proof must originate in verified server upload/finalization, never client JSON.

- **Historical acceptance needs a separate current-validity read.** Re-running `previewAcceptance` on an old record fails its recordedAt == current asOf check, by design for new writes. Do not use that failure as the sole implementation of historical acceptance attention. A read assessment must preserve the immutable original acceptance and determine current criteria/evidence/attachment/exception changes, including expired/revised/archived/superseded decisions, without manufacturing a new acceptance or changing task/milestone status.

- **The simple helper is not the authorization gate.** Plan-compatible `requirementFindings` checks scope/candidate/attachment ID presence and optional freshness only; with no max age it does not inspect future observation dates, attachment readiness, links or heads. Route/compiler authorization must use `evaluateRequirements`/`previewAcceptance`, not treat an empty simple-helper findings array as approval.

## Verified protections and limits

- Legacy migration explicitly sets observedAt/candidate/environment to null; its recordedAt is migration time. It preserves original text and does not create backdated acceptance or achieved status. No unknown observation date fabrication found.
- Aggregate assessment treats future observations/recordings as invalid support; unknown observation date remains visible, and unknown dates cannot meet a bounded freshness window. Scope equality prevents software evidence from satisfying physical/economic criteria; an exception remains separately recorded authority, not evidence reclassification.
- Exception checks require the exact current unarchived decision head, exact version, decided status, selected option, rationale, subject, scope, criterion IDs and unexpired grant. Revising/archiving/superseding a decision prevents its older grant from authorizing a new acceptance when the supplied heads are current. Historical versions remain available.
- Historical evidence selection requires an explicit historical flag; unresolved links and archived heads fail closed. Acceptance refs/schema reject unknown fields; supersession preserves the old record and rejects unknown/already-superseded targets.
- Ready attachment metadata alone is insufficient for aggregate support: digest, byte count, ready timestamp and trusted signature proof are checked. Ready-file reservation expiry is intentionally not treated as content expiry.

## Integrated storage review and authority correction

Reviewed the transitional Phase 3 compiler, composite adapters, reviewed importer, namespaces, attachment routes, undo command-group resolver and migrations through 0012.

**Found and resolved blocker: restore could resurrect a revoked owner decision grant.** The original compiler correctly minted `decision_owner_grants` only for explicit `decisions.decide`/`decisions.supersede`, not imported audit claims. However those operational grants survived normalized replacement. An owner could decide v2, revise to v3 (revoking v2 through its head), then restore an older bundle containing the exact v2 head/version/hash; the retained grant would authorize new acceptance using that imported version. The integrator has now added a claim-guarded owner grant deletion to `restoreEpoch`. Immutable decision history remains preserved; an explicit new owner decide is required after restore. The deletion participates in the same transaction, so failed restore retains authority with the original workspace.

Added `tests/decision-authority-restore.test.ts` with two real SQLite/compiler regressions: (1) v2 decide → v3 revoke → old-v2 restore loses trusted authority until fresh explicit decide; (2) an abort trigger on grant deletion rolls back restore and preserves grants, decision heads/versions and revision. Both pass. Scoped ESLint and full typecheck pass at this checkpoint.

Other inspected boundaries:

- `workspace-export.ts:exportWorkspaceBundle` uses read-only `getWorkspaceNamespaces`; it does not initialize or rotate server namespace state during backup preparation. Portable source metadata includes only the public audit namespace. Cursor secret/blob namespace are excluded from that source object; the attachment payload caveat below remains. Explicit workspace initialization owns creation. History GET still initializes its namespace configuration; that does not write planning/evidence records, but is a distinct initialization side effect rather than a completely write-free endpoint.
- Composite import splits explicitly cover declared tables, reject undeclared/duplicate/overlapping coverage and validate physical version identities. Projection is recomputed centrally instead of importing typed SQL columns. The closed owner table order puts evidence/decision heads before their versions and evidence versions before links; replacement deletes reverse that order. 0012 rebuilds the child evidence-links table while leaving its referenced parent intact, without unsupported `foreign_keys=OFF/ON` transaction toggling. Its retained FK is owner + evidence ID + version; requirement validity is enforced by the scoped reference validator rather than an FK to obsolete requirement identities.
- Imported decision records and imported `decision.decide` actor claims do not mint grants: compiler grant creation is gated on the actual current decision command. Restore invalidation closes the pre-existing-grant reuse hole. Imported old audit rows remain operational imported-history claims, never a current owner command group.
- Attachment content/upload routes authenticate first, perform owner-bound metadata lookup, require persisted owner namespace and reconstruct the exact owner UUID storage key before blob I/O. Ready download verifies actual bytes/hash/signature and returns private/no-store/nosniff headers. A foreign namespace inside imported metadata cannot redirect reads into another owner's files. Evidence snapshot omits storageKey/uploadMutationId and explicitly describes metadata-only recovery.
- `readAuditCommandGroup` resolves original workspace revision to exactly one retained mutation receipt, loads the complete bounded ordinal group and checks owner origin/actor and typed attribution. Undo submits original mutation identity plus a hash over every source event and the reference snapshot. Missing/pruned receipts safely disable this undo path rather than allowing a selected subset. The current ordinary undo implementation intentionally refuses normalized module edits and create/delete recovery; broader Phase 3 undo acceptance remains incomplete.

Remaining gates before claiming Phase 3 acceptance: real private blob binding and authenticated route tests; complete binary backup/restore (current exports are explicitly metadata-only); immutable historical acceptance current-validity UI; full lifecycle acceptance enforcement including permitted undo transitions; and all integrated browser failure/recovery journeys. These are unfinished acceptance scope, not evidence of a current cross-owner read or partial-write defect in this bounded storage review.

Additional integrated contract findings:

- **Portable attachment metadata currently includes the source blob namespace indirectly.** Although workspace namespace comments promise exclusion, `evidence-module.ts:single` exports the full typed attachment record, including `storageKey` (`attachments/<blobNamespace>/<id>`) and upload mutation identity. This is not an authorization token and does not bypass the route's owner namespace check. Nevertheless it contradicts the server-only namespace contract and should be resolved explicitly through a portable attachment metadata/provenance representation, rather than assuming source-object filtering removes it.
- **Backup manifests underreport missing attachment bytes.** `exportWorkspaceBundle` always emits `attachments: []`, including when `modules.attachments` holds ready files. `prepareWorkspaceBackup` then hardcodes `missingAttachments: []`; reconstructed manifests derive missing files only from that empty attachment manifest. The bundle's top-level `completeness: metadata-only` is accurate, but the backup manifest also lists the attachment metadata module as complete and says no attachment is missing. Derive excluded/missing file IDs from typed metadata or make manifest metadata-only completeness explicit before presenting recovery guarantees. No binary recovery acceptance is established by these metadata snapshots.
