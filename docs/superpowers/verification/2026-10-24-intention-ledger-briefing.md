# Intention-ledger briefing verification — 2026-10-24

This increment redesigns the owner briefing on every project tile around the owner's own intentions. The owner judged the previous card's layout unhelpful: it summarised the newest commits and tasks but had no notion of what they had set out to do, whether it was reached, or where the plan bent. The new core of the briefing is an **intention ledger**: each aim the owner stated in their own chat turns, where it was said, what became of it, and the points where the plan changed. A **project map** draws the project's areas, how far each is proven and what feeds what. Both carry forward from one briefing to the next.

The design was settled against a manual run of the same workflow on the owner's Trade Graph repository (27 cloud sessions and the repository's own research ledger), compared with a paragraph the owner wrote from memory. That run found six places where memory and record differed, which is the value the owner wanted from the card. The reference output stays outside the public repository.

## What changed

- **Contract, version 2** (`shared/project-briefing.mjs`, `.d.mts`): `aim`, `leftOff`, `areas` (id, name, state `proven | built | partial | open | paused | blocked | none`, done/total, note), one-way `links`, `aimArea`, `intentions` (date, title, outcome, state `reached | negative | changed | paused | not-reached | in-progress | open`, source, area, optional `bend` from/to/why, evidence refs, at most 24, newest first), `open`, `needsYou`, `tried`, `done`, `notDone`, `nextSteps`, `limitations`. Evidence gains `ownerTurns` coverage and `previous` (the run the ledger was carried forward from). Validation rejects unknown area ids, self-links, duplicate areas, cyclic maps, and a `previous` that names the run itself. A saved **version 1** report still validates and is projected to the version 2 shape for display (`upgradeBriefing`), with an empty map; nothing is written back. `previousLedger()` cuts the bounded slice (14,000 characters, oldest intentions dropped first) that rides into the next run.
- **Size bounds**: a briefing may now be 26,000 characters (was 9,600), still inside the 55,000-byte personal-channel delivery bound. The evidence statement bound of 10,000 characters is kept for every statement except one whose `sourceRecordId` is the briefing marker (`lib/evidence-validation.ts`); the marker string is unchanged so saved rows keep their identity.
- **Evidence pack** (`companion/briefing-evidence.mjs`): the readers now return up to 24 sessions of 60 messages per assistant (bounded by the readers' own file and byte limits); the owner's **user turns** are kept as a separate bundle (700 characters per turn, 40 per session, 28,000 in all), secret-filtered and path-redacted, with sessions newer than the previous briefing placed first and the remaining budget filled newest-first (`ownerTurnsFrom`, `selectOwnerSessions`). The clipped conversation excerpts stay as before. The bundle and summary carry the previous ledger; the work fingerprint does not include it.
- **Prompt** (`companion/briefing-prompt.mjs`): asks for the ledger, defines each state and bend, instructs the model to carry the previous ledger forward and record new bends against it, and defines the map. Business language and the no-identifiers rule are unchanged.
- **Runner and connector** (`companion/briefing-run.mjs`, `companion/personal-connector.mjs`): `runProjectBriefing` accepts `previous`, validates it, refuses one that names the current run, and stamps `version: 2`. The connector reads the previous ledger from its own private per-request backups for the same project and folder (newest completed briefing), so no protocol or server change was needed: the previous ledger is the device's own earlier claim.
- **Dashboard** (`lib/dashboard/model.ts`): `BriefingView.ledger` with labelled, toned intention rows (`isNew` when dated after the previous horizon), area rows, links and the bend count; the attention list reads `needsYou`. The evidence line names the owner's turns and the briefing carried forward from.
- **Card** (`components/briefing-card.tsx`, styles in `app/globals.css`): status, the aim, where we left off, the project map (layered layout computed from the links; clicking an area filters the trail; keyboard operable), the intention trail (newest first, seven shown then "show earlier", filters All / Plan changes / Still open, "new since" marks), how the plan changed, Needs you and Still open with next steps, and folds for what was tried, done and not yet, and how the briefing was put together.

## Addendum 2026-10-25: over-full PC request record

The owner's pre-publication recovery copy (native ZIP export of the live version 22) failed the restore validator with "Personal repository request is invalid" on both this increment and its base commit. The cause was not the briefing change: the live PC-connection record held 22 requests (repeated failed and cancelled folder pickers, one failed analysis, one failed and one completed briefing) while `validatePersonalState` admitted at most 20, and the server validates that record on every load. Deploying any build from this lineage would therefore have refused the record on its first contact with the PC.

Fix (`shared/personal-repository.mjs`, `.d.mts`): the validator's hard bound is now four times the queue limit, and `transitionPersonalState` prunes the oldest finished requests (failed, cancelled, consumed or result-less completed) down to the limit before applying any action; an enqueue prunes one more so the queue makes room by itself. Active requests and completed results the owner has not saved are never pruned, so "Recent connection requests are full" now appears only when twenty such requests exist. Covered by a new case in `tests/personal-repository.test.ts` that loads a 22-request record, converges it on the next poll, keeps the queued request, admits a new browse and still refuses a queue of twenty active ones; the 81-request hard bound is also checked. `tests/personal-repository*.test.ts`, `tests/project-briefing.test.ts`, `tests/backups.test.ts`, `tests/workspace-transaction.test.ts`, `tests/module-initialization.test.ts`: 115 passed, 0 failed; typecheck and lint unchanged.

How the live record exceeded the limit is not established from here; every branch in the repository carries the same limit and the same write-time validation, so the live version was built from a source that differs or the record was written through another path. After this fix the record loads, is pruned on the first PC poll, and the same recovery copy validates.
