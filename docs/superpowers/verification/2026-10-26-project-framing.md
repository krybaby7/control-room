## What changed

- **Workspace:** `Project.framing` preserves substantive text and line breaks, is empty by default, and rejects more than 2,500 characters and forbidden controls. `includeTaskPlanInBriefings` defaults to false. Older workspaces hydrate these defaults. Create/edit, planning serialization, native exports and restored bundles retain the fields. Generated empty/false/null defaults are omitted only by compact storage, preserving historical workspace checksums and exact byte accounting. `personalRepositoryKey` saves a folder association in the same atomic project-create command; duplicate associations are rejected, including archived projects.
- **Admission and state:** the server reads the project at admission and projects `ProjectFraming`: project identity, framing, workspace revision, inclusion choice, compact optional milestone/task lists and accurate totals. Opt-out lists are empty. Clients cannot supply framing or the legacy plan. Workspace revision fencing still prevents an admission from committing after its project read became stale. Owner job lists omit framing and legacy plans. State and companion validation require matching project identity. New completions also bind project name and every framing coverage field to the admitted payload.
- **Historical jobs:** old plan-bearing state remains readable without rewriting its hash. Active legacy briefs fail as interrupted before dispatch; they are never silently reinterpreted as framing. Saved or retained historical reports remain acknowledgeable after deterministic projection, with the original request digest still required.
- **Prompt and report:** `THE OWNER'S FRAMING` is labelled untrusted reference data, never instructions or a source of intentions. Empty framing must be disclosed and cannot be inferred from goals, tasks, old reports or chats. Whitespace-only framing is absent on transport; substantive framing is preserved verbatim. Optional task statuses cannot prove outcomes. V3 requires `fitOrDrift`, up to 480 characters, with one or two sentences assessing the bigger-picture fit or drift. New `source: plan` intentions are refused; historical plan provenance can carry forward.
- **Compatibility:** frozen V1/V2 validators read saved reports and pure projections supply an honest not-assessed fit-or-drift sentence and null framing provenance. Neither projection claims old briefings used framing. V3 allows 26,200 characters for the new sentence, historical inputs retain 26,000, and all reports retain the 55,000-byte bound. If an extreme historical report would exceed that byte bound after projection, only its projected copy shortens prose: last limitations first, then oldest intention outcome/bend/title text, then other prose arrays from the end. It retains every row, identity, date, state and provenance, preserves a substantive character in each field, and visibly discloses shortening in `fitOrDrift`. Saved originals remain unchanged; an explicitly saved V3 projection or later ledger can carry the disclosed shortening. The bounded previous ledger carries the new field and accepts older ledger shapes.
- **Screens:** the project editor labels framing “What this project is and why,” explains its role, and offers “Include my task plan in briefings.” The briefing card places fit-or-drift under the aim and uses immutable report metadata to say “Measured against your framing” or “No framing written yet,” with task-plan inclusion. Historical cards show the honest compatibility sentence without inventing provenance.
- **Folder creation:** registered PC folders with no associated project offer “Create a project from this folder.” It creates a folder-named project with blank framing and task-plan inclusion off, saves the mapping, and offers a separate briefing action. It makes no analysis or briefing request during creation. Durable bindings take precedence over temporary choices. Archived bindings offer restore guidance; unavailable mapped folders cannot silently select another folder. Unconfirmed saves remain blocked for reconciliation; original briefing requests retain their project/provider/request identity across recovery.
