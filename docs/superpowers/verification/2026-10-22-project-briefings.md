# Project briefings verification — 2026-10-22

This increment gives every project on the mission-control dashboard an owner briefing: a short plain-language status report ("where we're at, the last pieces of work and which are unfinished, what is done, what is not yet done, what needs a decision, next steps") written on the owner's PC by Codex or Claude Code from an evidence pack the companion assembles itself. It builds on the dashboard branch head `0e4e509` and adds no database migration, dependency, hosted-audience or paid-provider change. The briefing contract, the save command and the personal channel extension are the new shared foundation; the dashboard, the companion and the Repositories panel are the consumers.

## What the owner gets

- **Briefing card on every project tile** (`components/mission-control-panels.tsx`): status chip (on track, at risk, blocked, paused, unclear), the headline and reason, the last pieces of work with a finished/unfinished/unclear mark and where they happened (this PC, cloud, both, chats), what is still open from that work, done and not-yet columns, decisions needed, next steps, and a fold explaining what the briefing was based on (counts of local and cloud commits, branches, pull requests, chats and plan items, the writing assistant and observed model, limitations, and the technical references for engineers). Decisions a briefing raises also appear under **Needs you**.
- **Honest freshness**: the card says when the briefing was written and on which request, flags when new commits or uncommitted changes have landed since, shows a running or queued briefing with its assistant, and names the reason when the last attempt failed. A briefing completed on the PC is shown immediately and saved automatically; the previous saved briefing stays visible while a refresh runs.
- **Controls**: choose the folder (when the PC knows several) and the assistant, **Brief this project / Refresh briefing**, and a **Keep current** switch. Keep current records an owner policy per repository (assistant, minimum interval, default two hours); the PC refreshes the briefing by itself only when the repository's work fingerprint changed and the interval passed. Switching it off stops admissions at once.
- The existing technical analysis remains on the tile, folded under "Technical analysis for your engineers".

## Evidence pack (companion, read-only)

`companion/briefing-evidence.mjs` gathers, within fixed bounds (14 days, 24 branches, 160 commits, 25 pull requests, 5 chats per assistant, 10 messages per chat, 160 KB): recent commits on local branches with ahead/behind/merged against the default branch; one `git fetch --prune origin` using the PC's existing Git credentials with prompts disabled (unreachable GitHub degrades to "as last fetched" or "unavailable", never a failure); the cloud branches that fetch reveals (this is where Codex Cloud and Claude Code cloud sessions land their work); pull requests only when a signed-in GitHub CLI is present; uncommitted paths and a diff summary; and the last few Codex and Claude Code sessions for the repository through the existing bounded readers, now able to return several sessions. Commit subjects and chat messages that look like credentials are dropped and local paths are redacted. The owner's plan (goal, milestones, open and recently completed tasks) is projected by the server (`compactPlan`) when the request is admitted, so no client can attach a different plan. The model runs with no tools, receives one prompt (`companion/briefing-prompt.mjs`) that asks for business language and forbids technical identifiers outside the short evidence references, and its JSON is validated against `shared/project-briefing.mjs` (9,600-character bound, matching the evidence statement limit).

## Authority boundaries kept

- A briefing is an uploaded personal-PC claim saved as immutable owner evidence (`project-briefing.save`, marker `control-room-project-briefing-v1`), one active briefing per project and repository, refreshed by explicit evidence ID and version. Nothing in it accepts, completes, approves or spends; decisions it raises are shown, never taken.
- Owner-initiated briefings and keep-current policies are owner commands on the personal channel. Automatic briefings are admitted by the server only against an enabled policy, only when idle, only after the minimum interval since the last briefing or attempt, and only for a changed fingerprint; the device never chooses the project, assistant or plan. Restored backups disable every policy.
- No paid API provider is used: both assistants run through the owner's existing subscription sign-ins on the PC exactly as analyses do. Cloud chat transcripts remain unconnected; the briefing sees cloud work through GitHub, not through cloud chats.
