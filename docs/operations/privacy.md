# Draft and device storage privacy

Implemented 18 October 2026. Server drafts are separate owner-scoped records, not saved planning data or recommendations. Draft CAS revisions never advance the workspace revision or issue mutation receipts. Retention defaults to 30 days, at most 64 KiB per record and 100 active records per owner. Expired records are excluded from recovery; `expireDrafts` removes expired rows before reusing an expired draft ID. Conflicts preserve both the submitted client draft and the newer stored draft. A committed command may acknowledge a draft only after its committed receipt is confirmed, using the saved draft revision so a newer edit is retained.

Device persistence defaults off. Without trusted-device consent, each outbox instance is memory-only and closing the page loses that memory. Explicit trusted-device consent permits IndexedDB storage. Anyone with access to the browser profile, or code executing on this app's origin, may read these records. A JavaScript-held encryption key would not protect against that access. Operating-system device encryption is useful but is not an application guarantee. Do not store passwords, access credentials, device keys or executable approval authority in drafts.

The integration must derive the owner from its authenticated server response before calling `DeviceOutbox.open`. Never use a request body owner as authority. A different verified owner opens a different namespace. On 401 call `lock` immediately to hide all in-memory private content and invalidate asynchronous callbacks. Reauthentication creates a new instance only after proving the owner. Explicit logout/forget-device calls and awaits `forget` before navigating: it hides memory, invalidates other tabs through the supplied broadcast bus, waits for local pending writes, then removes the owner namespace. Supply `browserInvalidationBus` in browser integrations. No private owner identifiers are included in the outbox's sharable export envelope.

Queue and replay are explicit actions. Reconnection does not submit anything. Replay first looks up the original stable mutation ID: committed/conflict settles locally; unknown remains uncertain; only an authoritative retryable result permits sending the exact retained command and ID. The caller must never translate a missing receipt, retired receipt epoch, authentication failure or unreadable outcome into retryable. Reopening a stored sending item marks it uncertain. Inspect/export/discard remain available before replay. A quota failure is surfaced and retains the in-memory item; the UI must not label it durably saved.

Integration exports: `draftSchema`, `validateDraft`, `listDrafts`, `saveDraft`, `deleteDraft`, `expireDrafts`, `createDraftDebouncer` (one-second default); `DeviceOutbox`, `memoryDeviceStorage`, `indexedDbDeviceStorage`, `browserInvalidationBus`. Draft shape uses `id`, `entityType`, optional `entityId`, `baseRevision`, `baseSnapshot`, `changedFields`, optional `command`/`mutationId`, and `createdAt`/`updatedAt`/`expiresAt`. API adapters map editorKind/targetId/commandCandidate if needed. Read/save responses add `draftRevision`. Server CRUD must apply authenticated same-origin JSON guards and no-store responses outside these modules. Debouncer cancellation prevents queued work; the UI must additionally fence any in-flight save response by session generation before showing saved status.

Automated tests use isolated SQLite and injected memory storage: CAS races, owner isolation, expiry, bounded JSON, debounce/cancellation, opt-in versus memory-only closure, unknown outcomes, interrupted replay, cross-tab invalidation, session changes and quota rejection. Typecheck passes. Native IndexedDB transactions, real browser closure/restart, profile access, browser quota limits and physical-device privacy have not been browser-verified here. The broadcast test is an injected bus, not evidence of a live two-browser run. Device persistence cannot guarantee survival of browser eviction.
