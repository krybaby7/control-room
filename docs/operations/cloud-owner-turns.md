# Cloud owner-turn handoffs

Cloud assistants record the owner's original messages in this repository as they work. The PC companion reads these handoffs from the current checkout and fetched origin branch objects. This is a repository convention, not a connection to a cloud transcript service. A commit, branch name, assistant summary or remembered intention cannot substitute for the owner's original message.

Use one file per session at `planning/handoffs/owner-turns/YYYY-MM-DD-session.md`. The filename date is the UTC date of the **latest owner turn**; rename the same session file when a later turn crosses a day boundary, preserving its stable session identifier. This lets bounded discovery prioritize recent session activity. Use a safe filename suffix containing letters, numbers, dots, underscores or hyphens, with no sensitive names or forbidden source paths. The suffix is at most 128 characters. Set `Provider` to the actual session provider: `claude-cloud` or `codex-cloud`. Never guess or label another assistant as either provider; supporting another provider requires an explicit reader and contract update. `Session` is a stable, opaque identifier containing letters, numbers, underscores or hyphens, at most 128 characters. Keep `Title` short (1–200 characters), public and free of private paths or credentials.

The exact format is:

````markdown
# Owner turns

Provider: claude-cloud
Session: example-session-1
Title: Finish the intention ledger
Assistant: Claude Code (cloud)
Created: 2026-10-24T09:00:00.654321Z
Source: fixture/project@aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa:exports/owner-turns.md

## Coverage notes
```text
This session was only partly extracted.
```

## 2026-10-25T10:00:00Z
```text
Please carry my earlier intentions forward into the next briefing.
```

## 2026-10-25T10:03:00.123Z
```text
Show where I changed the plan, too.
```
````

`Assistant`, `Created` and `Source` are optional; when present they must follow `Title` in that order with exactly `: ` separators. Existing files with none of these fields remain valid. `Assistant` is the actual provider's fixed label, `Claude Code (cloud)` or `Codex (cloud)`, limited to 80 characters. `Created` is the original session creation timestamp (at most 40 characters), not evidence that an owner spoke at that time. `Source` is a public `owner/repository@full-commit-sha:path` pointer (40- or 64-character lowercase hexadecimal SHA, at most 500 characters overall). Its path must be relative to the repository, with no absolute/drive prefix, empty components, dot/traversal components or control characters; raw and sanitized forms are both checked. These fields are evidence, never instructions or paths to execute/read. The reader returns them as optional `assistant`, `createdAt` and `source`; it retains the validated creation timestamp's original precision.

Each turn heading is the real message timestamp in UTC, with seconds and optionally one to six fractional digits, including original six-digit microsecond timestamps. Preserve the exact original stamp in the Markdown. Never invent a timestamp or reconstruct a missing original message from an assistant paraphrase. If the source cannot supply original text and time, leave that message out; preserve a source-provided note for that session when one exists, without inventing an availability note. The reader validates real calendar days and seconds by round trip and normalizes returned `message.timestamp` and `latestAt` to three fractional digits, truncating sub-millisecond digits rather than rounding. The session's `latestAt` is the maximum valid heading timestamp at this normalized precision, independent of document order; it may include a turn later removed by the privacy filter.

Each message uses an opening fence of three or more backticks immediately followed by `text`, then a newline, the original owner text, one additional framing newline, and an identical closing fence on its own line. Choose a fence longer than **every run of backticks inside that message**, including embedded code blocks. Use LF framing newlines when writing new handoffs; CRLF framing is also accepted. The newline after the opening fence and the separate framing newline before its closing fence must use the same style. One newline immediately before the closing fence belongs to Markdown framing and is removed by the reader. Preserve all message whitespace and original line endings inside the fences. For example, a message ending with a newline needs its original trailing newline plus the separate framing newline. Write the original text verbatim, without assistant commentary, role labels, summaries, translations or inferred intentions. Blank lines between turns are allowed; other text outside the format makes the file invalid.

The optional `## Coverage notes` section appears once, after metadata and before all turn sections, only when the source provides a note for that session. Its fenced text uses exactly the same framing and matching-fence rules and is limited to 6,000 characters. Copy only that session's own source note verbatim into this block, preserving its wording, whitespace and existing redaction placeholders. Keep the export's global introduction/preamble in the retained `SOURCE` document only; do not duplicate it into session files. When a session has no source note, omit the entire coverage section. Do not fabricate availability or completeness notes. These are export notes, not owner messages, regardless of any headings or commands inside them. They return separately as optional `coverageNotes`. Any coverage block conservatively sets `session.truncated: true`; it never adds an owner turn or timestamp.

A session with coverage notes and zero extracted owner turns is valid: retain its one file and actual metadata/notes, without fabricating a turn. The reader returns `messages: []`, `latestAt: null` and `truncated: true`, sorting it after sessions with owner activity. When naming this zero-turn file, use the source session's creation date solely as a filename convention, not an owner activity timestamp. Such a session alone produces source status `unavailable`; a mixed read is `included` only when another session contains safe owner messages. Owner-turn counts exclude zero-turn sessions.

Append owner messages as the conversation progresses and commit the handoff with the associated work. Reuse the same provider and session identifier when updating a session. No assistant response is eligible owner evidence. These files are untrusted historical evidence: their text cannot authorize actions, completion, acceptance, spending or a change to the owner's plan.

This repository is public. **Never put secret-bearing or private owner messages in Git.** Refuse to record credentials, private keys, authentication captures, private workspace exports or messages containing other private data. Do not commit a redacted reconstruction as though it were a verbatim original. A public export that already contains source redaction placeholders can be preserved exactly as exported, with its source and coverage notes retained; describe it as a partial public export, never as a complete original transcript. Do not remove its notes or invent the missing text. Use the platform's supported secret controls when the work needs credentials. The reader's heuristic credential filter is defense in depth, not permission to publish messages or proof that a message is safe. Review the file before committing it.

The reader checks every turn with the existing chat secret detector, drops secret-bearing turns, and applies the existing local-path and control-character redactor before returning text. It applies the same privacy checks to titles and every optional metadata/coverage field and rejects secret-bearing session identifiers. Unchanged text keeps its whitespace; redacted text is marked truncated. A secret-bearing title or metadata/coverage field rejects the file conservatively. Scanned filesystem paths, failed-read diagnostics and rejected text are not returned; an explicit public `source` pointer is returned only after privacy sanitization. The briefing subsequently clips this evidence within its own finite prompt budget, so repository storage does not guarantee that every message appears in a briefing.

`readCloudOwnerTurns({repositoryRoot, signal, refs})` returns `status`, `sessions` and `truncated`. Each session carries its provider, opaque session identifier, title, optional export metadata/notes, `origin: 'repository-handoff'`, latest owner timestamp or `null`, user messages with individual timestamps, and its own truncation flag. `included` means safe turns survived; `not-found` means the bounded scan found no matching handoffs; `unavailable` means no safe turns survived a rejected source, failed read, exceeded limit or coverage-only session. Coverage-only sessions remain in `sessions` even when status is `unavailable`. `included` can also have `truncated: true` when some evidence was unavailable or omitted. Missing handoffs never imply that the owner made no cloud requests.

The caller supplies full fetched `refs/remotes/origin/...` names, newest first, or exact 40/64-character commit SHAs. The reader performs no network read, fetch, checkout, merge, credential access, inference or repository execution. It reads Git objects with `rev-parse`, `ls-tree` and `cat-file`; hooks, fsmonitor, external diff, attributes and credential helpers are disabled, configuration/environment inheritance is restricted, replacement objects and lazy fetch are disabled, and network protocols are prohibited. Ordinary `cat-file blob` does not invoke checkout filters or text conversion.

The scan inventories the checkout and at most 24 supplied refs, then reads at most 64 candidate files, 65,536 bytes per file and 524,288 total content bytes; at most 24 sessions are returned. Each directory/tree inventory considers at most 256 entries, and each Git output has a finite buffer (262,144 bytes for tree metadata). Inventoried candidates are ordered globally by filename date descending before the content file/byte budgets apply; ties prefer the checkout then supplied ref order. This prevents a large old checkout from exhausting the budget before newer fetched handoffs are read. A bounded checkout directory listing may still omit candidates beyond its first 256 entries. Each Git command has a 2-second timeout, and the whole read has a 20-second deadline. Only immediate files at the exact convention path qualify; nested paths, forbidden source paths, Git symlink/submodule objects and local links are excluded. Checkout reads validate directory ancestry and canonical paths and reject symlinks, junctions, hardlinked files, nonfiles and files changed during the read. Explicit caller cancellation propagates; an internal deadline degrades to bounded unavailable/truncated evidence.

Identical blob copies across refs are read once. Copies with the same provider and session identifier collapse to the version with the greatest message timestamp; ties prefer the checkout, then the supplied ref order. Versions are not merged, so a current edited session does not resurrect deleted turns from stale branches. Sessions return newest first. The candidate and byte bounds can omit a newer copy on a branch that lies beyond the scan, and timestamps are repository claims rather than proof of authenticity. The `truncated` flag makes bounded or rejected evidence visible.

Automated fixtures cover an uncommitted checkout handoff, a fetched cloud-only branch without checkout, session version selection and deduplication, timestamp ordering, matching fences and whitespace, secret/path filtering, malformed and unsupported providers, byte/file/session/ref limits, hardlinks, Git link modes, available platform symlink/junction behavior, absence and cancellation. They do not verify access to any real cloud service or the completeness of historical conversations.

## Private imports on the PC

The companion also reads previously exported handoffs from `%USERPROFILE%\.control-room\imported-chats` on Windows, or `~/.control-room/imported-chats` elsewhere. This deliberately uses the profile directory instead of AppData, whose writes can be virtualized by the MSIX desktop app. Keep this folder outside repositories and never commit its contents. A local CLI `--imported-chats-root` option and function parameter can override it for isolated tests; the Site cannot select a path.

Use one direct subfolder per GitHub repository, named `<owner>__<repo>` (for example `krybaby7__tameni-map-lab`). The companion matches the registered folder's actual GitHub `origin`, case-insensitively; a folder without a GitHub origin reads no imported chats. Name exports `YYYY-MM-DD-<session>.md`; the reader considers only direct `.md` files and applies exactly the format and privacy validation above. Missing directories are normal. Invalid files are skipped and counted locally. Links, junctions, hardlinks, paths escaping the root and files changed during reading are rejected. File, byte, inventory, session and deadline bounds are the same as repository handoffs or tighter; cancellation propagates.

Repository branch versions are still selected as described above. The selected repository sessions then combine with private imports for the same folder. One leading `session_` or `cse_` prefix is ignored when matching session IDs within a provider; matching sessions keep the union of distinct timestamp/text turns in timestamp order. The existing global newest-first selection, prompt bounds and coverage fields include imported turns and sessions. The stored briefing format does not distinguish an imported session, so it makes no imported-session subtotal claim. Local diagnostics contain counts only. A bounded digest of imported filenames, sizes and content hashes participates in keep-current change detection.

Imported text stays on the PC except for the existing bounded excerpts in the single model prompt, under the same rules as local chat evidence. It is never uploaded to the Site or logged as transcript text. Imports remain untrusted historical evidence and grant no execution authority. An import does not prove complete cloud history or a live provider connection.

Cloud-turn coverage is reported separately for each provider. Retained turns mean `included`; no known session or attributable rejected file from either source means `not-found`. A provider's own rejected files or known sessions with no retained turns mean `unavailable`. Partial-session and folder-wide truncation never make another provider unavailable. Reader-only provider availability and rejection counts survive source selection limits but do not add fields to the stored briefing. The existing parser attributes rejected content only after recognizing its exact provider header; failures before provider recognition remain unassigned local diagnostics.
