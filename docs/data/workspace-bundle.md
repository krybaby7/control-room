# Workspace bundle core

The Phase 1 pure/core API exports JSON `format: control-room`, `bundleVersion: 1`, an export timestamp, migrated planning, versioned named modules, attachment manifest, completeness and source metadata. Source metadata records the owner workspace revision, independent planning schema version, module content-hash watermarks and SHA-256 source hashes. Hashes are canonical JSON hashes; a module watermark denotes its actual observed snapshot, not a global operational sequence.

`exportWorkspaceBundle(db, serverDerivedOwner, options)` reads the owner revision and planning, scans registered module rows in pages of at most 200, repeats the module scans, then reads the owner revision/planning again. A revision or content mismatch retries, at most three times. Owner module rows include revision and content hash so mutable operational races are detected independently of planning revision. Audit scans include both owner-command and operational events. The implementation relies on all owner-command writes advancing the revision and immutable audit rows remaining immutable. It does not implement a distributed snapshot or prevent changes after the final observation.

Limits: 8 MB serialized bundle, 10,000 records per module, 40 levels of portable payload nesting. Module SQL uses the closed owner table reader; adapters cannot accept request SQL. Populated owner tables without an export adapter fail closed. Feature modules must register schema validators and reference validators; arbitrary configuration payloads are never implicitly exported. Unknown modules and versions fail closed. Receipts, credential/token/secret fields, executable approval/job authority and device keys are excluded. This key screening supplements schema validators and is not a guarantee that user text contains no sensitive information.

Planning is always top-level. The default registry includes only `audit_events` v1, append-only policy. Audit provenance is imported via namespaced historical records returned by `historicalAuditRows`; original actor identities are source claims. A future transaction adapter must append these records to the existing ledger and must never replace it or grant authority from source claims.

Attachments currently use an empty manifest and `metadata-only` completeness. Core import rejects nonempty manifests until a verified attachment adapter exists; this is not an attachment backup.

`ImportQuarantine` is bounded process-local staging, separate from active records. It copies raw bytes, hashes the exact bytes, retains invalid content for owner-scoped download, uses an expiry (default one hour, maximum one day), and caps retained stages (default eight, maximum twenty). Diagnostics contain path/code only, without raw imported text. Strict fatal UTF-8 decoding and JSON parsing run within the byte limit. Legacy planning v1/v2/v3 imports use the existing migration chain; they are planning-only previews and cannot justify replacement of normalized modules.

Preview reports record counts, new/deleted/changed IDs, module versions, target revision, current backup availability and attachment completeness. Invalid references from planning or module validators keep the import quarantined. `parsedForReview` checks owner, expiry, content hash and target revision and returns a copy, not executable authority.

This slice does not provide a restore command, API/UI, persistent staging, repairs, recovery snapshots or atomic multi-module writes. Integration must revalidate server-held staged content and references, require a complete recovery bundle, derive its mutation plan server-side, and use the sole workspace command transaction executor. Execution epoch changes, approval invalidation, job cancellation/reconciliation, schedule pausing and append-only audit merge belong in that transaction. Passing core tests does not establish these restore guarantees.
